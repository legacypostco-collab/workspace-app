# Контроль работы сервиса

Система наблюдения состоит из трёх независимых уровней.

1. Приложение считает ответы `4xx`, `5xx`, медленные запросы, ошибки фоновых
   задач, длину очереди и загрузку соединений базы. Содержимое запросов,
   адреса страниц и данные пользователей в эти показатели не попадают.
2. Серверный контроллер раз в минуту проверяет приложение, базу, Redis,
   очередь задач, планировщик, контейнеры, ресурсы узла, DNS, сертификат,
   заголовки безопасности, маршрут постоянного соединения, заполнение диска и
   индексных записей, неожиданные перезапуски контейнеров и свежесть копии БД.
3. Внешний сторож получает пульс успешной проверки. Если весь сервер или его
   сеть пропадут, именно внешний сторож сообщает о потере пульса.

## Установка на сервере приложения

```bash
sudo bash deploy/install_monitoring.sh /srv/consolidator-itunity
```

Контроллер запускается таймером `consolidator-monitor.timer` каждую минуту.
Текущее состояние хранится в
`/var/lib/consolidator-monitor/status.json` без персональных данных и секретов.

```bash
systemctl status consolidator-monitor.timer
python3 deploy/monitoring_controller.py --status
python3 deploy/monitoring_controller.py --no-heal
```

## Каналы сообщений

Нужно настроить минимум один канал: `MONITOR_WEBHOOK_URL` либо одновременно
`MONITOR_TELEGRAM_BOT_TOKEN` и `MONITOR_TELEGRAM_CHAT_ID`. Сообщение о сбое
отправляется после двух последовательных ошибок, повторяется не чаще одного
раза в 30 минут и сопровождается отдельным сообщением о восстановлении.

`UPTIME_HEARTBEAT_URL` должен принадлежать внешней службе контроля пульса.
`UPTIME_HEARTBEAT_FAIL_URL` используется для немедленной отметки сбоя, если
служба поддерживает такой адрес. Самопроверка на том же сервере не обнаружит
полное отключение питания или сети, поэтому внешний сторож обязателен для
боевого запуска.

## Автоматическое восстановление

После трёх подтверждённых сбоев контроллер может перезапустить только
прикладные контейнеры `web`, `worker` и `beat`. Между попытками выдерживается
15 минут. База, Redis, прокси и антивирус автоматически не перезапускаются:
для них нужен разбор причины, чтобы не усугубить повреждение данных.

Автовосстановление отключается через `MONITOR_AUTOHEAL=False` или для одного
проверочного запуска параметром `--no-heal`.

## Закрытая выдача показателей

`GET /metrics/` возвращает показатели в формате Prometheus только при наличии
правильного заголовка `X-Healthcheck-Token`. Без токена маршрут отвечает `404`.
Токен берётся из `HEALTHCHECK_TOKEN`; его нельзя передавать в строке адреса.

## Sentry

При заданном `SENTRY_DSN` фиксируются необработанные ошибки Django, Celery и
Redis. Перед отправкой из события удаляются пароли, токены, ключи, куки,
сеансы и коды двухфакторной защиты. `send_default_pii` отключён.

## Внешний экземпляр контроллера

На втором узле можно выполнять только внешние проверки:

```bash
MONITOR_PUBLIC_URL=https://consolidatorparts.com \
python3 monitoring_controller.py --external-only --no-heal
```

Этот режим проверяет публичную доступность, DNS, TLS, защитные заголовки и
маршрут постоянного соединения, но не имеет доступа к Docker и данным узла.

Если маршрут чата меняется, его нужно явно указать через
`MONITOR_WEBSOCKET_PATH`; стандартное значение — `/ws/assistant/`.
